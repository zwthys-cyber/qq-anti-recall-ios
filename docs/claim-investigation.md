### 已确认
- 用户截图确认第一次领取使 QQ 获赞总数从 28 增至 128。
- 后续提交返回名额不足，不能由此推断限制只针对 IP。
- 商品 83 的公开说明允许重复下单，同时明确要求上一笔订单显示已完成后再下第二笔。
- 商品元数据“允许重复下单”为“是”。重复下单权限不等于免费额度无限。
- 本次目标订单查询返回 1 条记录：`code=4`、`status=1`、`state=0`、`is_received=0`。
- 站点 `/api/orderStatusCodes` 将该订单显示状态解释为“进行中”。当前不能标记为已完成。

### 解释边界
订单页面通过 `code` 与站点状态表显示订单状态。不能只凭 `status=1` 认定完成，也不能把整个页面的“已退款”等筛选标签当成订单状态。
QQ 已到账与供应商订单标记完成是两个不同事实。“进行中”与名额不足同时存在，但尚未证实两者因果关系。
下一次提交前应先核对订单是否完成及免费额度是否恢复。没有验证更换 IP 有效，没有新增到账证据。

## 独立出口实验

原参考项目 README 明确描述出口 IP 与会话额度限制，并使用每个任务独立虚拟机为不同 QQ 领取；该经验不直接证明同一 QQ 可以持续重复领取。
来源：[参考项目说明](https://github.com/GaoZitian/qqqzz-card-claim#原理)。

按用户明确要求，在 [运行 43811263301](https://github.com/zwthys-cyber/qq-anti-recall-ios/actions/runs/43811263301) 进行了单次独立出口实验：
- 基准任务与领取任务分别使用 GitHub 托管 Ubuntu 虚拟机。
- 两个任务通过 HTTPS IP 观测服务取得 IPv4，用运行 ID 加盐后计算 SHA-256，在任务间比较；不输出原始 IP。
- 出口不同核验通过。此观测只针对观测服务，不证明供应商最终见到相同地址。
- 历史失败任务未记录 IP，因此不能证明本次与历史失败任务的 IP 不同。
- 领取使用全新浏览器会话，8 项行为测试及语法检查通过。
- 免费预览成功；实际提交 1 次；回执 HTTP 200，分类为 `quota_exhausted`；`order_accepted=false`。
- 未核实新增到账。本次实验证明独立任务运行仍可能被拒绝，不足以断言 IP 无关、QQ 号限制、订单限制或全站额度中的任一种是唯一原因。
- 一次性触发器已关闭。无循环提交、无代理池、无付费订单。

默认分支手动工作流新增可选 `verify_new_egress`，核验失败时不会进入订单步骤；领取源码仍固定到已有测试版本。
